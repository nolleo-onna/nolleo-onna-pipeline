# 놀러온나 — 설계 확정 & 역할 분배 회의

> **이 회의의 목표(딱 3개)**
>
> 1. MVP 범위 확정 — 무엇을 데모까지 만들고, 무엇을 Phase 2로 미루나
> 2. 도메인 경계 합의 — 누가 어느 테이블의 주인인가, 경계는 어떻게 참조하나
> 3. 역할 분배 — 세 사람이 각자 무엇을 들고 나가나
>
> **이 회의에서 안 정하는 것 (다음으로 미룸)**
>
> - API 명세서 (엔드포인트 시그니처) → 도메인 오너 정해진 뒤 각자 1차안
> - 코스 생성 알고리즘 상세 (Greedy 점수식, 대체 로직) → 별도 세션
>
> 진행 순서: **① MVP 커팅 → ② 도메인 경계 확정 → ③ 역할 분배**
> (설계 토론을 먼저 하면 시간이 다 날아갑니다. 범위부터 자릅니다.)

## 1단계 — MVP IN / OUT 커팅

**커팅 기준(사람이 아니라 질문으로 자른다):**

> "이 기능이 없으면 **데모 시나리오**가 안 돌아가나?"
>
> - 안 돌아감 → IN
> - 돌아감(있으면 좋지만 데모는 됨) → Phase 2

**합의가 필요한 데모 시나리오 (먼저 이걸 한 문장으로 못 박기):**

> 예) *"비 오는 날, 영도에서 5만원으로 둘이 데이트 → 코스 2개(감성/짠내)가 나오고 → '왜 이 코스인지' 근거가 보이고 → 카톡 공유"*
>
> 합의된 시나리오: ________________________________________

### 1-B. Phase 2 후보 (차별점이지만 데모 없이도 코스는 나옴)

**여기가 회의에서 제일 싸우는 곳입니다.** "차별점인데 빼도 되나?" — 빼는 게 아니라 *순서를 미루는* 거라고 프레이밍하세요.


| 기능                      | 미루는 논리                                                                  | IN으로 당길까? |
| ----------------------- | ----------------------------------------------------------------------- | --------- |

| 관광공사 코스 짠내 변환           | 1순위 어필이라 강력. 단 Greedy가 먼저 돌아야 가능 → 순서상 후순위                              |           |
| 오늘 축제 코스 자동 반영          | 1순위 어필. 축제 데이터 수집은 IN, "코스 자동 삽입"은 Greedy 안정화 후                         |           |
| 한끗(에디토리얼) 전체            | 콘텐츠는 사람이 채워야 함. 데모용 3개 수기면 충분, 시스템 전체는 Phase 2                          |           |
| 북마크/컬렉션/방문상태/리뷰         | 코스 저장과 별개. 데모 시연 길이상 우선순위 낮음                                            |           |
| 유저 제보 + 관리자 대시보드 + 자동숨김 | 운영 기능. 데모에서 안 보임                                                        |           |
| 개인화(활동로그·월별리포트)         | 유저 로그 0건에선 의미 없음. 문서에도 "제외" 근처                                          |           |
| 익명 유저 처리                | ERD에선 "익명 제거 확정"인데 기능표엔 "익명 제보" → **모순. 논쟁 포인트 ②**                      |           |


> ⚠️ **기능표 vs ERD 충돌 2건** 
>
> 1. **익명 유저**: 기능표 "익명 제보 Must" ↔ ERD "익명 사용자 제거 확정, user_id NOT NULL". 둘 중 하나가 거짓말. 제보를 로그인 필수로 할지 결정 필요.

## 1.5단계 — 화면별 MVP IN / OUT (와이어프레임 기준)

> 기능 리스트가 아니라 **와이어프레임에 실제로 그려진 요소** 기준.
> 화면은 5개: 홈 / 스팟 / 코스 / 한끗 / 마이페이지.
> 표기: ✅ IN(데모에 보임) · ⏸ Phase2(자리만 두거나 비활성) · ✂️ 데모용 더미(시스템은 Phase2, 화면엔 수기 3건)

> ⚠️ **와이어프레임 — 회의에서 반드시:**  
> 디자인은 **날씨·미세먼지·혼잡도**를 홈 메인 위젯 + 코스결과 "추천 이유" 핵심 UI로 *이미 전제하고* 그려졌음.
> 그런데 1단계에선 이 셋을 Phase 2 후보로 뺐음 → **빼면 홈/코스결과 화면이 텅 빔.**
> 선택지: (a) 셋 다 IN으로 승격 (b) 데이터는 IN, "추천 알고리즘 반영"만 Phase2이고 화면엔 *표시만* (c) 홈 위젯만 IN, 코스 반영은 Phase2.
> → **논쟁 포인트 ⑤로 추가됨 (아래 2단계 참조).**

## 2단계 — 도메인 경계 확정  

설계 "확정"은 컬럼 단위로 하지 않습니다. **경계 단위**로만 합니다.  
경계 합의 = "이 도메인 주인은 누구 / 다른 도메인은 이걸 어떻게 참조하나(직접 JOIN? ID 조회?)".

### 논쟁 포인트 ① — 파이썬(FastAPI)/Spring DB 공유 구조 ★ 최우선

> "누가 SPOTS_CORE를 채우고 누가 읽기만 하나"

- 현재 설계: 한 DB를 FastAPI(쓰기=수집/임베딩) + Spring(쓰기=사용자/코스)이 공유, 권한 분리 + 상태전이 규칙으로 방어
- 질문: *"왜 DB를 안 나눠? 왜 API로 안 주고받아?"*
- 답변: 모듈러 모노리스 + 파이프라인이 마스터 데이터 SoT이므로 공유, 단 §6 책임 매트릭스 / §13 상태전이로 충돌 방지

### 논쟁 포인트 ⑤ — 환경 데이터(날씨·미세먼지·혼잡도)를 MVP에 넣나 ★ 와이어프레임발

> 홈 메인 위젯 + 코스결과 "추천 이유" 칩 = 와이어프레임의 얼굴인데, 빼면 화면이 빔.  
> 동시에 이 셋은 외부API 3개(기상청·에어코리아·관광공사 혼잡) 추가 연동 + 캐시 테이블 + 코스 알고리즘 반영이라 **공수가 가장 큰 묶음.**

세 가지 선택지 — 회의에서 택1:

- **(a) 풀 IN**: 데이터 수집 + 화면 표시 + 코스 알고리즘 반영 전부. 어필 3순위 강하게 가져감. 공수 최대.
- **(b) 표시만 IN, 반영 Phase2** ← *권장 시작점*: 외부API 수집 + 홈/코스결과에 **표시**까지만. "추천 이유 칩"은 보여주되 알고리즘이 실제로 그걸로 코스를 바꾸진 않음(데모 멘트로 커버). 화면 안 비고 공수 중간.
- **(c) 최소**: 홈 위젯만 IN(단순 조회), 스팟/코스 내 환경요소는 Phase2(자리만). 공수 최소, 차별점 약화.

### 역할 분배 초안 (회의에서 확정)


| 사람          | 도메인             | 핵심 책임                                                               | 비고                                 |

> 분배 시 체크: ① 어필 1순위(TourAPI 깊이)는 D1=한나, 2순위(AI검색)는 D1·D2 협업, 3순위(플랜B)는 D2 → **어필 포인트가 한 사람에 안 쏠리게** 분산됐는지 확인.
